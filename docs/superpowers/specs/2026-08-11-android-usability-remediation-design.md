# Android 可用性整改设计

## 背景

当前 Android 客户端已经具备原生 Compose 页面、Room 数据库、WorkManager 队列、Android Keystore、供应商配置、项目版本树、历史统计和图片操作等模块，但现阶段更接近功能覆盖型开发样机，尚未形成可信的日常使用闭环。

截至 2026 年 8 月 11 日，当前基线证据如下：

- Android 代码最后一次集中更新停留在 2026 年 8 月 6 日的 `3b75fa4`。
- 已发布测试包为 `release/miaos-android-0.1.0-dev46.apk`。
- 应用版本仍为 `0.1.0`、`versionCode = 1`，当前包为可调试开发包。
- `testDebugUnitTest --rerun-tasks` 共 84 项通过。
- `connectedDebugAndroidTest` 在 API 36 模拟器执行成功；未注入配对地址的网络配对用例按设计跳过。
- `lintDebug` 为 0 个错误、20 个警告。
- `assembleDebug` 成功。
- 真实供应商、真实 Android 手机、真实相册/分享和同 Wi-Fi 扫码尚未形成可重复验收记录。

因此，后续整改不再以“页面存在”“请求 JSON 有测试”或“APK 可以安装”作为完成标准，而以全新安装后能否顺畅完成真实创作闭环作为第一判断标准。

## 目标

将 Android 客户端从开发样机推进到可供日常内部测试的版本，优先完成以下结果：

1. 全新安装后，不查阅外部文档即可完成供应商配置。
2. 使用用户授权的真实供应商完成文生图和图生图。
3. 失败时能看到可执行的中文原因，并能导出脱敏诊断信息。
4. 切后台、锁屏、断网和进程重启后，任务状态保持一致。
5. 项目与历史包含多张高分辨率图片时，不因同步解码原图出现明显卡顿或内存崩溃。
6. 生成正式签名的内部测试包，并具备稳定的版本递增和 GitHub 构建流程。

## 非目标

本轮整改明确不包含：

- Windows 客户端。
- 云端账号、云同步或妙生业务服务端。
- S3 自动同步。
- 视频生成入口。
- 会员、支付、社交或公开分享平台。
- 重做整套视觉设计。
- 在可用性闭环完成前继续扩充统计图表或供应商数量。

## 产品定位

### 第一阶段定位

Android 先作为能够独立生图、管理本机项目和历史的客户端。macOS 到 Android 的 `.miaos` 配置迁移继续只传输供应商、模型、默认设置、主题和密钥，不在第一阶段偷偷扩展为项目同步协议。

### 跨端数据定位

项目、历史和图片跨端迁移属于独立子项目。只有在 Android 可用性与稳定性阶段通过后，才进入“加密项目包导入/导出”设计；在该设计完成前，不向用户暗示 macOS 项目会自动出现在 Android。

## 设计原则

### 首装体验优先

首次启动不再只展示“从 macOS 导入配置”。页面同时提供：

- 使用内置供应商预设快速配置。
- 从 macOS 导入加密配置。
- 扫描一次性配对二维码。
- 添加 OpenAI 兼容自定义供应商。

内置预设负责提供供应商名称、类型、默认端点和官方支持的模型列表。用户只需要选择预设、输入 API Key、测试连接并保存。

### 先验证再保存

新增供应商时，输入新的 API Key 必须先完成一次受控连接验证。编辑已有供应商且没有输入新 Key 时，可以保留已有密钥并单独测试。连接测试不得把 API Key、Authorization 或上游响应正文写入 UI、Room 或日志。

### 失败可诊断

生成失败记录使用稳定错误代码和失败阶段，例如：

- `AUTH_FAILED`
- `RATE_LIMITED`
- `NETWORK_UNAVAILABLE`
- `REQUEST_TIMEOUT`
- `INVALID_RESPONSE`
- `IMAGE_DOWNLOAD_FAILED`
- `SOURCE_IMAGE_INVALID`
- `UNKNOWN_FAILURE`

用户界面显示简短原因、建议操作和诊断编号。详细诊断写入应用私有目录，只保存脱敏后的错误类型、HTTP 状态、阶段、供应商类型、模型、时间和应用版本，不保存 API Key、Authorization、图片字节或完整上游正文。

### 图片按显示需求加载

所有列表缩略图使用 Coil 异步加载，限制解码尺寸并启用内存/磁盘缓存。列表改用 `LazyColumn` 或 `LazyVerticalGrid`，不再在普通 `Column` 中一次性构建全部图片，也不在主线程调用 `BitmapFactory.decodeFile()` 解码完整原图。

原图只在全屏预览、分享或保存时读取。预览继续限制可视尺寸，避免把多张 2K/4K 图片同时驻留内存。

### 后台任务诚实可见

WorkManager 继续承担持久化调度，Room 继续作为用户可见任务状态的事实来源。运行中的长任务提供通知和明确状态。用户取消运行中任务时，客户端保证：

- 立即把本地任务标记为已取消。
- 请求 Worker 停止后续轮询和结果写入。
- 若供应商已经接收请求，不承诺能撤销远端扣费或远端生成。

### 真机证据高于模拟器证据

每个里程碑都必须区分：

- JVM 单元测试。
- Android Runtime 仪器测试。
- API 36 模拟器 UI 验证。
- 用户授权真实 API Key 的供应商验证。
- 真实 Android 手机验证。

缺少后两项时，只能标记为“代码/模拟器完成”，不能称为“正式可用”。

## 分阶段交付

### P0：真实可用闭环

交付首次启动向导、内置供应商预设、先验证再保存、真实生图验收、失败分类和脱敏诊断。P0 结束时，全新安装必须能在两分钟内完成配置并生成第一张图片。

### P1：日常稳定性

交付 Coil 图片管线、惰性列表、后台通知、运行中取消、状态恢复和核心 Compose UI 自动化测试。P1 结束时，包含至少 100 条历史和 30 张高分辨率图片的数据集仍可顺畅浏览。

### P2：移动端价值补齐

在 P0/P1 通过后，单独设计加密项目包导入/导出，使用户可以显式迁移某个项目及图片，而不是引入云同步。该阶段不得修改现有 `.miaos` 配置协议的职责。

### P3：正式内部发布

交付 release 签名、版本策略、GitHub Actions、内部测试发布说明、升级验证和真机矩阵。P3 结束时生成不可调试的签名 APK/AAB，并保留可追踪的 SHA-256。

P3 只依赖 P0/P1，不依赖 P2。项目包迁移可在首个稳定内部测试版发布后独立推进，避免大型跨端协议阻塞基础可用版本交付。

## 验收总门槛

整改完成必须同时满足：

1. 全新安装路径无需手工输入已知供应商的端点和模型 ID。
2. 至少一个主要供应商完成真实文生图和图生图。
3. 401、403、429、超时、断网、非法响应和图片下载失败均有明确反馈。
4. 任务切后台和进程重启后不重复请求、不错误复活已取消任务。
5. 历史、项目和预览不再在主线程同步解码列表原图。
6. Compose UI 测试覆盖首装、配置、生成任务卡、失败详情和项目/历史导航。
7. Debug、Lint、JVM 测试、仪器测试和正式签名构建全部通过。
8. 真机验收报告明确记录设备、Android 版本、供应商、测试路径和未完成边界。
